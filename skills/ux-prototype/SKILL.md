# UX 单文件原型协作

**标注**是总称；**交互说明**补充产品、业务、功能与交互逻辑，长期保留；**修改意见**提出待处理的变更。程序维护单文件中的 PRD、标注与历史，AI 负责理解需求和修改内容。

## 修改已有稿

提示词已给出修改意见、目标元素、工作文件和完成命令时，直接据此执行，无需再读任务清单或上下文文件。DSH 发送与复制给外部 Agent 使用同一流程，适用于文案、布局、交互和业务逻辑修改：

1. 从意见和目标片段开始编辑工作文件；遇到动态内容、依赖或需求歧义时再补读相应源码、PRD 或说明。设计确有变化时才读设计资料。
2. 完成后执行提示词中的 `finish WORKFILE --summary "实际改动"`。程序计算 diff、记录历史、处理完成状态并保存交付，不需要另写 `changes.json` 或分别调用 `apply`、`complete`。默认完成本轮全部所选意见；只完成部分时用 `--resolve ann-a,ann-b`，一条也未完成则用 `--resolve none`，不能把未完成的意见报为完成。

需要 PRD 局部替换、说明更新、按需读取参数或处理交付冲突时，查 [修改与提交](references/dsh-task.md)；没有准备好的工作文件时，查 [独立 CLI](references/cli.md#已有协作稿的局部修改)。

## 内容与范围

- 只处理本轮授权范围，保留稳定锚点、人工内容、未选意见与既有历史。交互说明不当作待办，不自动清理或改成修改意见；未分类旧标注先由人工确认类型。
- PRD 仅在本轮需求实际受影响且允许修改时补读相关段落，通过 `prdOps` 提交局部替换，不重新输出全文。程序维护当前正文与可还原的增量历史。
- 检查围绕实际改动及尚未确定的行为展开，没有每轮必跑的浏览器、截图或测试清单。程序负责格式、历史与保存一致性；不要重复计算哈希、运行全量检查或为了交付自建验证脚本。不把未检查的效果说成已通过。
- 新增或修改交互说明以代码实际行为为准，产品规则与待实现意图明确标示。PRD 可在相关段落下引用说明 ID，不引用修改意见。涉及说明、引用、锚点或跨页面定位时查 [文件规范](references/file-format.md)。

## 新建与导入

- **新建原型：**默认按同级 [opentiny-ux](../opentiny-ux/SKILL.md) 制作业务 HTML；用户指定其他设计依据时沿用其选择，再按 [独立 CLI](references/cli.md) 封装，OpenTiny 新稿显式使用 `--design opentiny`。
- **导入现有 HTML／补充说明：**按 [导入现有稿](references/import-existing.md) 保留业务视觉与行为，移除已知旧协作外壳，报告迁移结果并交付新文件，不因导入套用 OpenTiny。

脚本需要 Node.js 22+，无须安装 npm 依赖。命令使用提示词提供的真实路径；仅在参数不清楚时查看对应命令 `--help`。
